# Паттерны проектирования на Go

Учебные реализации 23 классических паттернов GoF. Паттерн — способ решения повторяющейся задачи проектирования. Применять его стоит, когда он упрощает конкретную задачу; для небольшого кода часто достаточно обычной функции или структуры.

Примеры использования находятся в [`cmd/main.go`](cmd/main.go). Запуск из корня проекта:

```bash
go run ./cmd
```

## Порождающие паттерны

Управляют созданием объектов и отделяют его детали от использующего кода.

| Паттерн | Для чего и когда применять | Пример в проекте |
| --- | --- | --- |
| [Singleton — Одиночка](patterns/singleton) | Выдаёт один общий экземпляр. Нужен, когда ресурс действительно должен быть единственным; глобальное состояние усложняет тестирование. | Пользователь, инициализируемый через `sync.Once`. |
| [Builder — Строитель](patterns/builder) | Собирает объект по шагам. Удобен при множестве настроек и необязательных параметров. | Пошаговое заполнение пользователя. |
| [Prototype — Прототип](patterns/prototype) | Создаёт объект копированием образца. Полезен для заготовок с уже настроенными данными. | Клонирование пользователя и разрешений. |
| [Factory Method — Фабричный метод](patterns/factory) | Делегирует создание продукта конкретному создателю. Применяется, когда общая логика должна работать с разными реализациями продукта. | Создатели email- и SMS-уведомлений. |
| [Abstract Factory — Абстрактная фабрика](patterns/abstract-factory) | Создаёт согласованное семейство продуктов. Нужна, когда несколько связанных типов должны выбираться вместе. | Frontend- и backend-команды. |

## Структурные паттерны

Описывают способы связывать объекты и составлять из них более сложные структуры.

| Паттерн | Для чего и когда применять | Пример в проекте |
| --- | --- | --- |
| [Adapter — Адаптер](patterns/adapter) | Приводит существующий API к ожидаемому интерфейсу. Полезен при интеграции сторонних библиотек и старого кода. | Telegram-клиент за интерфейсом уведомлений. |
| [Bridge — Мост](patterns/bridge) | Разделяет две независимо изменяющиеся части и связывает их через интерфейс. Позволяет избежать отдельного типа для каждой комбинации вариантов. | Рестораны и виды пиццы. |
| [Composite — Компоновщик](patterns/composite) | Позволяет одинаково работать с одиночным элементом и группой. Подходит для деревьев и вложенных структур. | Файлы и папки с общим методом подсчёта размера. |
| [Decorator — Декоратор](patterns/decorator) | Добавляет поведение обёртками с тем же интерфейсом. Полезен, когда дополнительные возможности нужно комбинировать. | Цепочка уведомителя, логирования и вывода времени. |
| [Facade — Фасад](patterns/facade) | Даёт простой вход в сложную подсистему. Скрывает от клиента порядок взаимодействия нескольких компонентов. | Обслуживание клиента через официанта и кухню. |
| [Flyweight — Легковес](patterns/flyweight) | Разделяет повторяющиеся данные между объектами. Нужен при большом числе объектов с одинаковой частью состояния; общие данные желательно не изменять. | Несколько книг с общим `BookType`. |
| [Proxy — Заместитель](patterns/proxy) | Контролирует доступ к объекту через тот же интерфейс. Применяется для кеширования, проверки прав, отложенной загрузки или удалённого доступа. | Кеширующий загрузчик видео. |

## Поведенческие паттерны

Определяют алгоритмы, распределение обязанностей и взаимодействие объектов.

| Паттерн | Для чего и когда применять | Пример в проекте |
| --- | --- | --- |
| [Strategy — Стратегия](patterns/strategy) | Позволяет выбирать взаимозаменяемый алгоритм. Полезна, когда одну задачу можно выполнять разными способами. | Оплата картой или наличными. |
| [Observer — Наблюдатель](patterns/observer) | Уведомляет подписчиков о событии. Применяется, когда отправитель не должен зависеть от конкретных получателей. | Уведомление покупателей о поступлении товара. |
| [Command — Команда](patterns/command) | Представляет запрос отдельным объектом. Позволяет передавать действия, откладывать выполнение, строить очереди и при необходимости реализовывать отмену. | Кнопка с командами включения и выключения устройств. |
| [State — Состояние](patterns/state) | Меняет поведение объекта в зависимости от состояния. Подходит для жизненных циклов с разрешёнными действиями и переходами. | Созданный, оплаченный и отправленный заказ. |
| [Chain of Responsibility — Цепочка обязанностей](patterns/chain-of-responsibility) | Передаёт запрос по обработчикам. Каждый решает, продолжать ли обработку; подходит для последовательных проверок и маршрутизации. | Авторизация, проверка роли и наличия товара. |
| [Template Method — Шаблонный метод](patterns/template-method) | Фиксирует порядок алгоритма, позволяя менять отдельные шаги. Полезен для процессов с общим каркасом. | Приготовление чая и кофе. |
| [Iterator — Итератор](patterns/iterator) | Даёт последовательный доступ к элементам, скрывая устройство коллекции. Позволяет держать независимую позицию каждого обхода. | Generic-итератор среза. |
| [Mediator — Посредник](patterns/mediator) | Сосредотачивает правила взаимодействия объектов в координаторе. Полезен, когда прямые связи участников становятся запутанными. | Чат и доставка сообщений участникам. |
| [Memento — Снимок](patterns/memento) | Сохраняет и восстанавливает состояние, не раскрывая его содержимое хранителю истории. Подходит для отмены изменений и контрольных точек. | Редактор и история снимков текста. |
| [Visitor — Посетитель](patterns/visitor) | Выносит операции над разными типами объектов в посетителей. Удобен при стабильном наборе типов и частом добавлении операций. | Подсчёт площади и вывод фигур. |
| [Interpreter — Интерпретатор](patterns/interpreter) | Представляет правила небольшого языка объектами и вычисляет выражения. Подходит для простых формул и предметных языков. | Дерево чисел, сложения и умножения. |
